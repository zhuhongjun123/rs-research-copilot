# 开发调试记录 · 问题与定位过程

> 本文档按**问题类别**而非时间线整理。每条包含：现象 / 误判 / 定位手段 / 根因 / 修法 / 教训。
>
> 记录这些是因为：**这个项目真正的难点不在功能，而在「让结论可信」**。
> 下面 23 个问题里，有 9 个属于**误报治理**——它们全部来自「想当然」，
> 每一条都只能靠**回到原始字节**才定位得到。

## A. 环境与依赖

### A1 · 在线抓取工具读 PDF 只返回标题

| | |
| --- | --- |
| **现象** | 用在线网页抓取工具读厂商技术 PDF，返回内容仅 122 / 138 字符（基本只有文件名） |
| **误判** | 一度以为这些 PDF 是扫描件、没有文本层，准备放弃这批语料 |
| **定位** | 改**本地 PyMuPDF** 提取同一文件 → 100,765 字符、12,687 汉字。**PDF 本身完全正常** |
| **根因** | 在线提取服务对中文 PDF 的文本层支持不可靠，不是数据的问题 |
| **修法** | 解析必须自己跑；**不依赖任何在线提取服务** |
| **教训** | 工具报「提取失败」时，**先怀疑工具，再怀疑数据格式**。换一条独立链路复验是最快的判别法 |

### A2 · conda-forge 装不上 Docling

- **现象**：`pixi add docling` → 依赖 `deepsearch-glm` 在该源无候选版本
- **根因**：该包只有 PyPI 有
- **修法**：Docling 走 PyPI；并在 README 写明，避免使用者重复踩坑

### A3 · Docling 与主环境依赖硬冲突 → 隔离成独立环境

- **现象**：`typer==0.27.2`、`huggingface-hub==1.31.0` 被 conda solve **pin 住**，docling 要求不同版本 → 无解
- **试过但无效**：`index-strategy = "unsafe-best-match"`；把 embedding 也交给 PyPI
- **修法**：`no-default-feature = true`，把解析器隔离成**独立环境**，主环境保持干净，解析器以子进程 worker 调用
- **教训**：依赖冲突不一定要在一个环境里硬解。**隔离一个"离线 worker"往往更干净**

### A4 · Windows 上其它 GDAL 发行版遮蔽本环境 DLL

- **现象**：`rasterio` / `fiona` / `pyogrio` 导入失败，报 `DLL load failed: 找不到指定的程序`
- **定位**：**逐项追加 PATH 目录做二分** → 锁定 `Anaconda\Library\bin`（内含 `gdal.dll`）。
  本机同时装了 Anaconda 与 ArcGIS 10.8，PATH 上有两份 GDAL
- **无效的尝试**：`os.add_dll_directory()` —— 错误的 DLL 在更早阶段已被解析，事后补目录无效
- **修法**：写 `scripts/bootstrap_env.py`，以**干净 PATH** 启动解释器（仅本环境 + 系统目录）
- **教训**：`pixi run` 把本环境目录排在 PATH 最前**并不足够**；Windows 的 DLL 解析在依赖链上会漏出去

## B. 外部 API 与数据契约

### B1 · `linkMode` 在 HTTP API 里是**字符串**，不是整数

| | |
| --- | --- |
| **现象** | 自检报「5 篇期刊论文里没找到任何可用 PDF」，但手工 curl 明明能拿到 |
| **定位** | 照 Zotero **源码常量**把 `linkMode` 写成整数 `(0,1,2)`，而 **API 返回的是 `"imported_url"`** |
| **后果** | `linkMode not in (0,1,2)` 恒真 → **所有附件被静默过滤** |
| **修法** | 字符串与整数两套都认（SQLite 侧确实是整数），内部归一成名字 |
| **教训** | **官方源码常量 ≠ API 序列化形式**。文档给的枚举值不一定是线上传的形态，**以实测响应为准** |

### B2 · `/fulltext` 返回 JSON 而不是纯文本

- **现象**：拿到的「全文」以 `{` 开头
- **根因**：返回体是 `{"content": "..."}`，必须解包
- **教训**：接口返回形态要实测；文档没说清的地方，一次真实调用就够

### B3 · 附件路径是 URL 编码的

`file:///F:/ZoteroPaper/storage/RKA4MEL9/Zhang%20%E7%AD%89%20-%202015…`
→ 必须 `unquote` + 处理 `file:///F:/` 的前导斜杠，否则 `Path` 不可用

### B4 · 数据目录不能硬编码

- **事实**：官方默认是 `~/Zotero`，但本机通过 `prefs.js` 的 `extensions.zotero.dataDir` 指向 `F:\ZoteroPaper`
- **修法**：按「环境变量 > prefs.js > 默认」顺序发现
- **附带发现**：`C:\Users\<user>\Zotero` 是两年前的**旧目录残留**，容易被误当成活动库

### B5 · 「模型单价为 0」≠「零余额可用」

- **现象**：文档写明 SiliconFlow `BAAI/bge-m3` 是 **¥0/M token**，实测却全线 `402 余额不足`
  （`bge-m3` / `Pro/bge-m3` / `Qwen3-Embedding-0.6B` / `bge-large-zh` 全部 402）
- **根因**：平台要求账户有正余额才能调 API，与模型单价无关
- **教训** | **价格页数字不能替代一次真实的 API 调用验证**

### B6 · 固定维度模型不能传 `dimensions`

- **现象**：`400 code 20015 The parameter is invalid`
- **根因**：`bge-m3` 是**固定 1024 维**（不支持 MRL 降维），无条件发送 `dimensions` 会报错
- **修法**：**只在用户显式设置 `EMBED_DIM` 时才请求降维**；预设里的维度只用于 `EmbeddingSpec`（指纹与索引元数据）
- **教训**：**「声明维度」与「请求降维」是两件事**，不能混

### B7 · 限流会让 SDK 静默退避重试

批量吞吐实测（64 条一批）：

| 批次 | 耗时 | 每 chunk |
| --- | --- | --- |
| 16 条 | 0.24 s | 15 ms |
| 32 条 | 0.33 s | 10 ms |
| **64 条（第 1 次）** | **61.26 s** | **957 ms** |
| 64 条（第 2 次） | 0.68 s | 11 ms |

第一次慢了约 **90 倍** —— 不是模型慢，是**触发限流后 `openai` SDK 自动退避重试**。

- **修法**：批量入库**自己控速**（令牌桶 + 按 `Retry-After` 退避）；评测脚本加指数退避（5s/10s/20s）并**把重试次数暴露出来**
- **另**：SiliconFlow 会返回 `429 TPM limit reached`，不加处理会让评测跑到一半崩掉
- **教训**：不能依赖 SDK 的隐式重试 —— 否则进度不可预测、日志看不出原因

### B8 · 思考模型在短输出下会超时

`Qwen/Qwen3-8B` 是思考模型，`max_tokens` 给小了会超时；改用 `deepseek-ai/DeepSeek-V3`

## C. 文本抽取

### C1 · 数值抽取：第一版正则命中 **0 处**

**这是整个项目的核心难点。**

第一版按「`指标 = 数值`」写正则 → 在 4 篇真实论文上**命中 0 处**。

实测到的书写形态**至少 8 种**：

```text
R² ≈0.73                          约等号
R ² of 0.981                      上标被拆成「空格+²」
R 2 reduced from 0.055 to 0.0036  上标被拆成「空格+2」；区间式
an RMSE of 0.0125                 「指标 of 值」
reduced RMSE (23.88 mm/month)     括号 + 单位
bias < 0.001, RMSE < 0.05         不等式
reached ~0.02                     波浪号近似
A VHRR                            单词内被插入空格（反向噪声）
```

**科学论文的数值是散文式表达，不是键值对。**

**归一化层（不可省）**：上标拆分、破折号 → 减号、全角 → 半角、数字内空格、
**小数点被渲染成冒号**（`0 : 055` → `0.055`）、移除 U+FFFD。

**连接段策略的三次演进**：

| 版本 | 做法 | 结果 |
| --- | --- | --- |
| 1 | 枚举连接词（`= : of is was reached (`…） | 必然漏，只抽到 **21** 条 |
| 2 | 盲扫「不含数字的字符」 | 抽到 **66** 条，但会**跨分句** —— 把 `LST bias using DEMs matched to the 5000 m` 里的 5000 当成了 bias 值 |
| 3 | **白名单 token 扫描** | 既不枚举完整连接串，也不跨分句 |

**效果**：命中 **0 → 66 条**。

### C2 · 指标词表不能写死

论文（GRSL）抽到 **0 条**，查原文发现它**根本不用 R²/RMSE/Bias 这套词** ——
报告的是 `0.004 decline of discrepancies` 这类**领域特有表述**。

→ **C1–C6 必须指标无关，或支持用户自定义指标词表**，否则会**静默漏掉整篇论文**。

### C3 · `context` 字段静默为空 —— 相对/绝对偏移混用

- **现象**：`NumericFact.context`（用于人工核验）是空的，**但不抛异常**
- **根因**：`num_end` 是相对 `rest` 的偏移，却直接拿去切 `text`
- **修法**：换算回绝对坐标 `match.end() + num_end`
- **教训**：**这类 bug 不抛异常，只让字段静默为空。自检必须断言字段内容，不能只看「没报错」**

### C4 · 句末判定：为躲小数点，把「数字后句号」也躲掉了

- **现象**：C3 把**校准前**的 `Bias` 与**校准后**的 `RMSE` 拿去互比
- **原文**：`… an RMSE of 0.02. After calibration … Bias reduced to 0.003`
- **根因**：句末正则用 `(?<!\d)` 排除小数点 → **`0.02. After` 不算断句**
- **修法**：改为「标点后跟**空白 + 大写字母**（英文）或 CJK」才算断句。
  小数点后必跟数字（无空白），自然不误判

## D. 误报治理（本项目最贵的一课）

真实论文**不该有内部矛盾**，所以误报数是这个工具的死穴。
实测误报数的演化：

```text
0 → 8 → 0（4 篇）→ 23（12 篇）→ 1 → 0
```

### ⚠️ 最关键的一条：小样本上的「完美指标」是假象

**4 篇语料上误报为 0**，把语料扩到 **12 篇**后，一夜之间多出 **23 条误报**。

> 凡是在小样本上得到的「完美指标」，在扩大样本前都不要写进任何结论 —— 包括简历。

### D1 · 区间声明被当成两个冲突值

- **原文**：`(R² reduced from 0.055 to 0.0036)`
- **误判**：`R² =0.055` 与 `R² to0.0036` 被当作两个互相冲突的独立值
- **修法**：`relation == "to"` 的端点**不参与等值比较**

### D2 · 盲扫窗口跨分句

- **原文**：`Figure 5 shows the impact on the LST Bias. At the 5000 m scale…`
- **误判**：盲扫窗口跨过英文句号，把 **5000（尺度）** 当成了 Bias 的值
- **修法**：白名单 token 扫描（见 C1）

### D3 · context 窗口太窄，把对象括号截断

- **现象**：对象抽成了 `strong`（邻近形容词），而不是 `TRI`
- **根因**：context 只取左侧 20 字符，把 `(TRI)` **截断** → 括号正则匹配不到
- **修法**：左侧窗口 **20 → 70**（context 仅用于人工核验与对象抽取，宁宽勿窄）

### D4 · 「指标 token 子串匹配」既误杀又放过

- **两个方向的错**：
  - 括号里装的就是「指标+值」本身（`(R² ≈0.75)`）→ 剔掉数字后只剩指标名 `r² ≈`，
    **被当成对象** → 误报
  - 想用「指标 token 是否为子串」判定，但 `R²` 归一后只剩**单字母 `r`**，
    `"r" in "tri"` 恒真 → **误杀合法对象 `TRI`**
- **修法**：**剔掉数字与指标名后，看还剩不剩实词**（残余字母 ≥2 才认）

### D5 · `partition` vs `rpartition` —— 取到了前一句

- **原文**：`… was strong, reaching R² = 0.75. In the discussion we again report for TRI R² = 0.21.`
- **误判**：`ctx.partition(metric)` 取的是**第一个** `R²`，于是第二条的对象被抽成前一句的 `strong`
- **修法**：改 `rpartition`（最后一次出现）

### D6 · 右侧对象只取首词 → 地类名撞车

- `evergreen needleleaf forests` 与 `evergreen broadleaf forests` 只取首词会双双缩成 `evergreen`
- **修法**：取前 3 个实词

### D7 · 「同句内多批合法站点数」被当成矛盾

- **原文**：`… 2 sites from the AmeriFlux Dataset, 2 sites from the European FluxNet Dataset, and 11 sites from a Tibetan dataset`
- **误判**：同一句里多批站点数是**合法**的，区分它们的是**数据集名**
- **修法**：C1 的对象改为取**右侧数据来源**，并在第一个句读处截断

### D8 · 通用词被当成「对象」→ 14 条误报

- **现象**：扩到 12 篇后，C2 报出 14 条，对象是 `low` / `day` / `compared` / `method` /
  `coverage` / `regions` / `std` / `achieved` / `correction` —— **都不是实体**
- **根因**：退路抽出的「对象」大量是通用词，两组数字本属不同对象，强行归为一组就是误报
- **修法**：新增 `distinctive_subject()`，**只信任三类**：
  ① 来自括号（`(TRI)`）② 缩写（原文中以全大写出现）③ 含连字符/数字的型号。
  退路抽出的普通词**一律不信任**（并设通用词黑名单）

### D9 · 表格单元格拼接 → 假的「数学不可能」

- **原文**（表格被解析器拼成一行）：
  ```text
  … Surface Pressure (hPa) … R.RMSE RMSE 0.22 | … R.Bias Bias 1.65 …
  ```
- **误判**：`(hPa)` 属于**另一列**，RMSE 0.22 与 Bias 1.65 分属**不同行**，
  却因「同块同句 + 共享对象 hpa」被拿去互比
- **修法**：**表格块不参与跨指标关系判定**（单事实检查如 `R²∈[0,1]` 照常）
- **理由**：表格拼行后单元格邻近关系本就不足为凭 —— 与「宁漏报不误报」一致

### D10 · 括号内的指标别名被取了后文的值

- **原文**：`… with a RMSE (R²) of 34 W/m² (0.53)`
- **误判**：`(R²)` 是 **RMSE 的别名括号**，`34` 是 RMSE 的值，被当成了 R²
- **修法**：**指标被括号包住时**直接跳过 —— 取值关系是歧义的，**宁漏报不误报**

### 三条防误报护栏（最终沉淀为代码纪律）

1. **对象抽不准 → 放弃比较**（宁漏报不误报）
2. **区间端点 / 不等式 → 不参与等值比较**
3. **数学关系只在同一对象的同一句内成立**（跨句比较必出误报；表格块也不参与）

## E. 评测方法学

### E1 · LLM 对照组曾静默跑成 0%

| | |
| --- | --- |
| **现象** | A 组显示「检出 0/12，耗时 0s，0 tokens」 |
| **危险之处** | 它看起来像是一个**结论**（"LLM 完全找不到问题"），实际**根本没调 API** |
| **根因** | `run_eval.py` 只 import 了 audit 模块、没经过 `config` → **`.env` 从未加载** → `build_chat()` 返回 `None` → 直接跳过 |
| **修法** | ① `load_dotenv()` 提到包入口 `src/rsrc/__init__.py` ② 评测脚本加**护栏**：LLM 不可用时**立即报错退出** |
| **教训** | **静默降级会产出「看起来合理的错误结论」，比直接崩掉危险得多。** 凡是对照组结果为全零，先怀疑工具链，再相信结论 |

### E2 · 注入器本身必须满足检查器的前提（三次同类）

做 ground truth 的代码出问题时，**症状永远看起来像「检查器漏报」**——

| 现象 | 真因 |
| --- | --- |
| 注入的 C1 抓不到 | 注入时**重新拼了**来源名（`from AmeriFlux`），而原文是 `from the AmeriFlux Dataset`；两边对象串不同，检查器**正确地**判为不同来源 |
| 同上（第二次） | 来源短语只吃到首个大写词，注入点插在了 `Dataset` **之前**，被逗号截断 |
| 注入量加大后出现**级联** | `0.74 → 0.369 → 0.239 → 0.194` —— 注入器每次都挑到**上一次改过的**那个事实；12 处注入里大量重叠，**检出率不可信** |
| C5 注入的缺陷**必然**抓不到 | C5 判定是「**同一对象**用了不同单位」，改的那个没有同对象的第二个出现 → **没有可比对象** |

> ⚠️ 这时去"修"一个本来正确的检查器，**会把真的能力改坏**。
> 与 Day 2 那次「指错了行」同源：作者口头核验与代码证据冲突时，**回去看原始字节**。

### E3 · 测量方法本身会骗人

- **首次粗测** `22,307 ms/条` → 那是**首次调用把模型初始化也算进去了**（5 条样本）。
  预热后实测 **293 ms/chunk** —— **慢了 76 倍**。
  → **性能测量必须先预热、样本量要够**
- **成本估算**：Day 0 抽样得 26 s/篇 → 外推全库 5 小时；Day 2 用真实出版版实测 **113 s/篇** → 15 小时。
  → **便利样本不代表总体，成本估算必须用目标总体的随机样本**

### E4 · 注入器签名与调用不一致

`inject_all` 统一传 `(blocks, facts, used)` 三个参数，但某个注入器只接受两个 → `TypeError`。
→ **统一签名**比各处 `try/except` 干净。
